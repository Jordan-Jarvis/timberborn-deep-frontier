### Moddable Timberborn integration details

The author's `ModdableTimberbornDemo/MStarter.cs` shows opt-in registry configuration, including `UseDependencyInjection()` and `UseMechanicalSystem()`. The installed DLL confirms `TogglableEnterableEffectComponent`, `TogglableEnterableTickEffectComponent<TData>` and `WorkplaceTogglableContainer`. These subscribe to actual native enterer/worker events; they do not reserve seats or calculate routes. Use the native attraction for the restaurant before adding any supplementary visitor effect.

Mechanical modifiers operate on the native mechanical node's input/output values. They are appropriate for upgrades and operating modifiers; they do not make a generator's nominal output its demand. Existing industrial shaft tests remain the authority for our physical sockets.

### Recipe and research constraints

The [author's recipe guide](https://github.com/datvm/TimberbornMods/blob/master/Docs/ModdableRecipes/README.MD) and installed DLL establish these constraints:

- Author locks from the outset. Retrofitting a lock onto a recipe already selected in a save needs an explicit migration decision.
- Keep a usable baseline recipe in a multi-recipe building. The author documents undefined behavior if every recipe is locked. Gate construction/commissioning for machines whose only recipe is advanced.
- Use visible locked entries and a localized prerequisite description so players know what comes next. Keep exact recipe IDs and an explicit project-to-recipe mapping.
- `ModdableRecipePersistentUnlocker` persists permanent unlocks. `UnlockLocally` and `ModdableRecipeBuilding` also exist in installed 11.0.0; do not assume global/local changes are interchangeable.
- Live recipe changes reapply production and can discard current progress. Static balance belongs in source blueprints; runtime modifiers need deliberate timing.
- The author reports a recipe-selector conflict with Better Healthcare. Our Hospital should use native care/attraction contracts and must not assume that separate mod is required.

Installed Scientific Projects exposes `RequiredId`, `ScienceCost`, faction selection, custom unlock-condition providers and unlock events. A custom condition returns a reason when unavailable. Its registry rejects custom unlock conditions on stepped/daily projects; use one-time certification projects for this design. `AlternativeRecipesSPs/Services/ProjectRecipeUnlocker.cs` is a useful author example of applying unlocked projects on load and on new unlock events. It is reference code, not an implemented Deep Frontier adapter.

### Water and automated-machinery helpers

TimberCommons' `IgorZ.TimberCommons.Stockpiles.GoodAmountTransformHeight` reads Manufactory inventory and subscribes to inventory changes. It can move a named transform according to stock. The inspected 1.23.0 implementation updates the **first** matching height entry for a changed good, and its `OnExitFinishedState` is empty. It also mixes an initially captured world Y with later local Y assignment. Verify lifecycle, raised placement and multiple surfaces before adoption. It does not cover our native model-child assembly, empty visibility or operating flow/wheel conditions. Do not run two components against the same water transform.

Bobingabout's installed readme and `Bobingabout.AutomatedManufactory.dll` describe `AutomatedManufactoryAnimationController`, `AutomatedManufactoryPowerConsumptionSwitch`, and `AutomatedManufactoryParticleController`. These target Manufactory readiness without requiring a Workshop worker. They are relevant to high-power automated processing; they do not implement coolant safety or nuclear waste custody.

## Hooman Stairs and internal doors

[Hooman Stairs](https://steamcommunity.com/sharedfiles/filedetails/?id=3682012904) has a 1.1 Workshop listing. Author package **2.0.2** (minimum game **1.1.2.4**) and source commit `1e686b1f48e8495e551802b57a4f5809cebd1f01` were downloaded for inspection. They are **not installed or enabled**. Exact download, hashes and raw manifest are in [`hooman_stairs_dependency_1_1.json`](../tools/hooman_stairs_dependency_1_1.json).

The Workshop lists **Harmony + Vertical Nav Mesh**; the downloaded manifest lists Harmony only and spells its version field `MinVersion`. Keep both observations. [Vertical Nav Mesh](https://steamcommunity.com/workshop/filedetails/?id=3631491885) is tagged 1.1 and addresses vertical path marker meshes; it is not a multi-door building authoring API.

The inspected Hooman DLL/source connects distinct finished stacked entities using their single positioned entrances. Its base-building filter includes dwelling, workplace and stockpile; attraction-only bases are excluded. It registers grouped graph edges, adjusts accessibility and handles district obstacles. No arbitrary multi-entrance registration API was found in this version.

It is a valuable example of graph lifecycle, but our four doors belong to one entity. The native `BlockObjectNavMeshBuilder.CanAddBlockingEdge` already exempts an edge that this builder explicitly added with the same start, end and group. Test authored native interior edges first. Native Double Lodge's inspected paths are roof routes, not proof of a multi-floor interior. District reachability, route visualization, hidden interior movement and exit positioning remain test requirements.

Do not reproduce Hooman's global `DistrictRandomDestinationPicker.GetRandomDestination` exception-suppression finalizer or its global FixedSlotManager change. Its footprint inference is also not the source-authoring approach requested here. No Hooman implementation was copied into Deep Frontier.

## Other Workshop candidates and obsolete libraries

- [CustomTools](https://steamcommunity.com/sharedfiles/filedetails/?id=3619414212) is tagged 1.1 and provides base classes plus blueprint tools, with Harmony and Moddable Tool Groups requirements. It is a candidate for future area selection or factory controls. It is not currently installed; its package version/API acceptance remains pending. Ordinary entity panels do not need it.
- [TimberAPI](https://steamcommunity.com/sharedfiles/filedetails/?id=3288241660) is explicitly deprecated for 1.0. Do not add the old framework for this project. The separately installed UIBuilder package is a different item.
- [Moddable Prefab U7](https://steamcommunity.com/sharedfiles/filedetails/?id=3447837683) deliberately errors on 1.0 according to its author. Use official blueprints and current spec/template APIs instead.

# Building walkways and adaptive railings

Latest decision, 2026-10-20: decks must accept **player-built native paths**, like vanilla platforms. The restaurant's `PlatformDeck` migration is documented in [grid alignment](art/grid-alignment.md). The built-in outdoor roads described below are the historical implementation still used by buildings awaiting migration; their earlier native passes do not validate the new contract.

Target: Timberborn 1.1.2.8. A shared feature for Deep Frontier buildings, starting with the kiln. Service decks and stairs must support actual beaver travel. Valid adjacent paths must produce openings in the railings, restored when the paths are removed. Use native building navigation.

Restaurant, Hospital and Grocery author connected doorways on layers 0, 2, 4 and 6, with rooftop access and clear construction terraces. The redesigned waterfront Fishery instead has three doors across layers 0/2; its smaller hatchery has a low bank-side entrance and dock routes. Hospital, Grocery, Fishery and Hatchery have passed actual native walking, stairs, supported platforms, selective rails and saved continuity. Restaurant seating/service passed, while its wider rotation and rail-seam checks remain separate. See [civic building integration](civic-building-integration.md) and `tools/STATUS.md` for exact per-building coverage.

Height interfaces follow the [authored layer contract](art/height-layout.md): crusher/kiln decks at layer 2; quarry decks at layers 1, 3, 5 and 7. Supports and ladder endpoints are generated from these levels; players supply external vanilla stairs. Detailed machinery retains its proportions. One Blender Z unit equals one grid layer; native centered coordinates add no vertical half-cell offset. Explicit horizontal bindings and industrial runtime acceptance are recorded below.

## Integrated implementation and acceptance

`tools/asset-pipeline/industrial_layouts.py` owns artwork origins, footprints, safe route cells, fractional walking positions and reciprocal boundary ports. The exported `*-Game.blend` scenes are derived from the reviewed scenes. No bounding-box fitting or artwork scaling is used. Minor deck dimensions may change for clearance, with the reviewed layout and doors preserved.

The native building graph supplies internal road edges and one-way outward boundary edges. `BuildingWalkway` owns a separate native navigation object that blocks both directions at closed ports. It checks completed paths and their authored reverse road edge, transformed through their actual placement, or a completed factory with a reciprocal opening. This prevents a sideways stair or an unfinished path from opening a rail. Mesh visibility requires the actual instant graph connection. Placement changes remove old blockers before installing the new coordinates. Do not query the preview graph to decide whether to remove a regular blocker: native instant changes also enter that graph, making such a test circular.

Each rail run is divided at exact cell boundaries in the exporter. Opening one port hides only its beam pieces and interior posts; neighboring rail panels and boundary posts remain. Connection-only plank lips meet the cell edge. Shaft-facing quarry rails are permanent. A native `IPathTransformer` translates selected native path corners onto the authored lanes; it does not replace route selection.

Static evidence: `outputs/industrial-integration/static-checks.json` checks exact model-node bindings, animation tracks, directional port edges and seam foundations. `route-clearance-diagnostics.json` checks floors and body clearance along sampled flat routes. The industrial scenes passed those sampled checks; native builds 15/17 subsequently verified the shaft, stair, platform, under-deck, rail, movement and saved-graph cases recorded below. Static sampling alone is not proof of every placement or pose.

The opt-in `-deepFrontierWalkwayAcceptance` harness only runs in the save with district marker `Deep Frontier Acceptance Fixture`. Create that disposable copy with `tools/create_industrial_acceptance_save.py`. The harness uses native terrain and finished-building APIs and logs validity, path add/remove/rebuild, a sideways staircase and two adjoining crushers. It must not run against a normal settlement. Current runtime outcomes and remaining checks are tracked in `tools/STATUS.md`.

## Verified native examples

The imported vanilla `Buildings/Housing/DoubleLodge/DoubleLodge.Folktails.blueprint.json` defines five navigation edges at elevation 1 inside a 2×2×2 building: four two-way edges around its upper circuit and one edge to its entrance. `TripleLodge.Folktails` defines four edges inside a 3×2×2 building. Both use `BlockObjectNavMeshSettingsSpec.EdgeGroups`, `AddedEdges`, `IsTwoWay` and `GenerateFloorsOnStackable`. Their groups set **`IsPath: false`**: these are walkable routes, not proof of district-road behavior. These Folktails examples establish an engine contract without making our Iron Teeth content depend on that faction.

Native `Path.blueprint.json` marks its four outgoing links `IsPath: true`, declares `PathSpec`, and occupies `Path`. Native `Stairs.IronTeeth` has lower/upper horizontal connections plus a two-way vertical edge, `PathSpec` and `StraightStairsSpec`. Its height provider assumes the native one-cell slope. Adding a collider or copying that spec onto an entire factory does not make an arbitrary long staircase navigable.

Installed source inspected with ILSpy is saved under `outputs/navigation-api-1.1.2.8/`:

- `NavMeshObjectUpdater.AddManuallySetEdges` in `Timberborn.BlockSystemNavigation` transforms explicitly authored grid coordinates through the building orientation. Stackable-floor generation creates regular movement edges. Occupations, auto walls and blocked edges must agree with the route; do not remove machinery collision indiscriminately.
- `IConnectionService.CanConnectInDirection` and `IPathService.IsPath` in `Timberborn.PathSystem` support connection checks. The implementation distinguishes road links, entrances and `IPathConnectionEnforcer`. Ordinary path lookup includes previews and unfinished paths, so final openings must be distinguished from previews and incomplete bridges.
- `DynamicPathModel.ValidateSize` rejects an owner larger than 1×1×1. This limits a **visual component**, not navigation inside a multi-cell building. Do not use it as evidence that a large building cannot contain native paths.
- `MergeableObjectModel` also requires a 1×1×1 owner and normally merges matching template names. It does not establish arbitrary factory-to-road railing adaptation.
- `IModelUpdater.UpdateModel` is called by `BlockObjectModelController`. Native navigation listeners can drive updates. Exact lifecycle and model-node switching still need in-game verification.

### Connected gears and shafts

The installed `Timberborn.ModularShafts` assembly confirms the user's analogy. `ModularShaftVariantFinder.FindBestVariant` evaluates six directions using actual mechanical transputs and placement previews. `ModularShaftModelUpdater` implements `IModelUpdater`, picks the matching oriented model and replaces the instance only when the variant changes. `MechanicalConnectorActivator` separately shows/hides connector pieces when facing transputs are added or removed. These are connection-driven visual systems; they do not supply walking routes.

For factory rails the corresponding public movement API is `INavMeshService.AreConnectedInstant`, checked in both directions. `INavMeshListenerEntityRegistry` supports event-driven updates through `IInstantNavMeshListener`. This avoids per-frame neighborhood polling and uses the graph after its update. Native `IPathConnectionEnforcer` lets an adjoining ordinary path point toward an explicitly authored factory opening even though the factory does not use the 1×1×1 `DynamicPathModel`.

## Reusable implementation

Use the housing-style native navigation spec for authored building routes. Road-network behavior is a separate explicit choice. Exclude machines, furnace interiors, roofs and storage bays from the route graph.

The shared Blender helper is `tools/asset-pipeline/walkway_geometry.py`. `RailAssembly` creates stable, separate post and panel nodes. The kiln uses it for all nine outer runs and emits `CementKiln-rail-manifest.json`. These rails are no longer welded into the architecture. An opening can hide multiple panels and an intermediate post; leaving a post in the opening is unacceptable. Structural columns and stair handrails remain independent.

`src/DeepFrontier/Scripts/BuildingWalkway.cs` now implements the shared adapter and its Game-only configurator. `BuildingWalkwaySpec.Openings` contains each ID, local `Inside` and `Outside` grid cell, and exact `HiddenNodes`. `BlockObject.TransformCoordinates` applies placement, rotation and flipping. `Awake` rejects duplicate IDs/edges, non-adjacent or unequal-height cells, inside cells outside the building volume, empty node sets and missing/ambiguous finished-model nodes. Shared node visibility is the union of currently open portals, so another closed opening cannot restore a post still needed by an open one.

The controller registers native instant-nav listeners only while finished. Actual openings require a finished native path or a neighboring factory with an exactly matching reverse port, plus a traversable native edge. Removing the connection restores the authored panels/posts. Construction preview path orientation reads the preview object's authored connection separately; it cannot open the finished factory's rails. There is no custom pathfinding, polling, Harmony patch, alternate node lookup or missing-data substitution.

The official Mod Builder compiled and installed the shared component. The current crusher, kiln and both quarry blueprints contain `BuildingWalkwaySpec`, native route edges, explicit collision and exported rail-node bindings. Industrial run 15 passed 35 rail visibility/navigation assertions, including shared decks, a rotated crusher, sideways stairs, unfinished paths, native stair upper exits and removal/rebuilding. All six ground-to-deck native route queries passed twice. A real beaver reached eight targets, including shared crusher decks, the kiln's rear gallery and the quarry's upper ladder gallery and return to its engine-room approach. See the current status document for persistence results and coverage limits.

The source rail manifest describes artwork coordinates; `industrial_layouts.py` explicitly registers them to the game grid. Do not round or automatically scale the model to invent bindings. Deck elevations, route cells, stair endpoints, collision, building access and openings are authored together. Preserve the reference design while making connection geometry agree with actual grid cells.

### Grid alignment and space below decks

The native district route display uses cell centers. Offsetting only a beaver waypoint can hide a mesh conflict from a custom route check while the displayed line still passes through a rail. Flat lanes are now authored at `(x + 0.5, y + 0.5, z)` in `industrial_layouts.py`; the deck edges and rails must physically clear those lanes. Stair endpoint positions remain explicit. The latest alignment pass retains the existing rooms and door positions and adjusts deck edges and small service details within the same overall footprint.

Placement and mouse selection have separate contracts. `BlockObjectSpec.Blocks` controls occupied grid cells; `CollidersSpec` controls picking. Reserving `All` throughout the rectangular size prevented paths, shafts and tubeways beneath visibly open catwalks. `tools/industrial_occupancy.mjs` now authors structural regions with unoccupied space elsewhere. Rooms, machinery, bracing and stairs remain reserved. Open support bays use native `Corners` and `Top, Corners` platform occupations, which do not intersect the `Bottom, Path, Middle` occupation of native shafts and tubeways. Selection boxes cover occupied sections, slabs and posts instead of one bounding box enclosing every void.

The quarry's surrounding ground footings use `Floor, Top, Corners`; its extraction core alone retains 25 exact `Top` foundations. This is necessary because `UnderstructureFinder.FindStrict` includes ground foundation cells with exactly Top, Corners or their combination. Mechanical transputs now cover occupied side and rear frames, with additional crusher front connections. `TransputMap` registers ports independently of occupancy, but shaft preview discovery queries registered block objects. Keep the authored ports on occupied frame cells and verify actual generator → shaft → factory power.

Integral stair flights have been removed. Players supply native Iron Teeth stairs in the cleared approaches; the upper exits connect to new adaptive FrontAccess rails and the kiln's RearAccess rail. Crusher/kiln reach layer 2 using two vanilla stairs and a supporting platform; quarry reaches layer 1 using one. Existing doors and machinery retain their layout. Integral quarry gallery ladders remain.

Deck support is declared on the slab immediately below each horizontal route cell. The walk cell remains Floor|Bottom|Path, allowing native Platform and DoublePlatform Top/Corners occupations to coexist. The native MatterBelow rule reads `Stackable: BlockObject` below the new platform. Actual equipment still blocks occupied space, and ladder hatches supply no artificial slab. Run 15 accepted five deck stacks of Double Platform + two Platforms + roof Path, including a rotated crusher and the quarry's upper gallery. Twelve under-deck placements and three solid-room rejection checks also passed.

The opt-in native acceptance fixture places paths, power shafts and tubeways under each building and a rotated crusher, then checks that solid rooms still reject paths. These tests are separate from rail connectivity, production, visible traversal and save/reload. Consult the current status for actual runtime results.

## Acceptance

### Native idle workers at arched entrances

User direction: enclosed opaque facades with windows and arched entrances; workers should stand at the doorway while idle. Source-confirmed in installed 1.1.2.8: `SimpleManufactoryBehaviorsSpec` registers `WaitInsideIdlyWorkplaceBehavior`, which uses `WalkInsideExecutor` and then `WaitExecutor.LaunchForIdleTime`. `Enterer.Enter` hides the character initially. `WorkplaceSlotManager` assigns a native `SlotManager` slot and shows the worker; `WorkshopWorkerHider` delegates to `WorkshopWorker.UpdateVisibility`, which shows the character specifically while `WaitInsideIdlyWorkplaceBehavior` is running and hides it otherwise. The native Smelter blueprint combines `TransformSlotInitializerSpec` (`SlotKeyword: Entrance`), `WorkplaceSlotManagerSpec` and `WorkshopWorkerHiderSpec`. Smelter uses Sitting; `Forester.IronTeeth` proves **ForcedIdle** is an authored standing-idle animation key.

The exported models now contain native `#Slot#Entrance` transforms at their existing arches. The producing generator restores the slot initializer/manager/hider together and uses ForcedIdle. No replacement idle AI or decorative beaver is used. Alignment, worker visibility, starvation/no-power/full-output conditions and save/reload still need in-game observation. Evidence: `outputs/navigation-api-1.1.2.8/{Timberborn.WorkSystem,Timberborn.Workshops,Timberborn.EnterableSystem}.cs`, `WalkInsideExecutor.cs`, `WorkshopWorkerHider.cs`, `WorkshopWorker.cs`.

### Quarry ladders

The installed `Tobbert.Ladder` **1.0.0.4** package has a `version-1.1` folder and was loaded in settlement run 13. Its Iron Teeth `Ladder` is a separate 1×1×1 path object. The empty public `Ladder.LadderSystem.LadderSpec` registers a decorator whose `OnEnterFinishedState` resets/rebuilds its own `BuildingNavMesh` and the path object's mesh at **owner.Coordinates**. Actual vertical travel comes from blueprint `AddedEdges` (0,0,0) ↔ (0,0,1), `IsPath=true`. A blocked group contains a one-way rear link; the start coordinate is explicitly unblocked. There is no arbitrary multi-port ladder configuration on this spec. Exact data/hashes: `tools/ladder_dependency_1_1.json`; installed DLL inspection: `outputs/ladder-api-1.0.0.4/Ladder.decompiled.cs`. Public repository main contains an older implementation, so do not treat it as matching this binary.

The quarry reference model has a separate ladder mast with landings at source Z=1,3,5,7, a 0.76-wide open hatch, and a gallery at each upper landing. The lift bucket travels in a different bay. Three original ladder mesh nodes and independent rail nodes are retained for export; the source access manifest describes physical coordinates, not guessed navigation cells.

Integration order after model review:

1. Assign the model an explicit grid origin/footprint and occupations, preserving its art proportions. Author walking/standing cells, shaft exclusions, support and selection collision together. The current five-tile seam and native mine understructure check must be reconciled with the larger quarry at their producing sources.
2. Use native building navigation for integral routes, with separate unit vertical edges at every ladder level. Do not add `LadderSpec` to the entire quarry expecting it to discover internal ladder positions. Prototype native vertical travel and district reach on one two-level segment first.
3. For player-placed Ladder pieces, reserve actual empty one-cell bays and support at the base. Six pieces would span Z=1→7; their authored costs would total 24 Logs + 36 Planks, with one 250-science unlock. Do not double-render our integral ladders and dependency ladders in the same bay. Choose and document the shipped construction model before declaring the dependency required.
4. Bind gallery openings to the existing `BuildingWalkwaySpec` only at real adjoining path cells. Attach/removal checks must include the upper end of a ladder, rotations, previews and unfinished objects. Preserve rails at the shaft itself.
5. Observe workers reach the top gallery and return, then test hauling, construction/removal and save/reload. Native path availability is distinct from climbing animation; verify actual appearance instead of inventing an animation API.

Both quarry blueprints activate integral native routes, including one-cell vertical edges through the ladder mast. Run 15 moved an actual beaver from the native stair approach to the upper gallery and back down to the engine-room approach. This establishes native traversal for that arrangement. The installed Ladder mod remains available for separately placed ladders; it is not used as a hidden alternate implementation.

### Native quarry understructure

Installed `UnderstructureFinder.FindStrict` checks foundation blocks whose occupation is exactly Top, Corners, or Top|Corners, and requires all selected coordinates to find the same named understructure entity. `BlockOccupationsExtensions.IsTopOrCornersOrBoth` confirms this exact comparison; it is not an arbitrary size-equality check. This suggests a larger quarry can retain a dedicated seam-aligned foundation patch while its surrounding support blocks are authored separately. That is a source-supported implementation option, not verified placement. Do not scale the old five-tile blueprint or impose the seam requirement on every new footprint cell accidentally. Inspect overlapping occupations, ground support and all rotations before shipping. Evidence: `outputs/navigation-api-1.1.2.8/Timberborn.UnderstructureSystem.cs`.

Verify beavers using all intended decks and both stairs, workplace access, hauling, same-level path attachment, wrong-height paths, path removal/rebuilding, previews, incomplete construction, all building rotations, neighboring factory connections and save/reload. Exposed edges retain rails; routes cannot cross machines or gaps. Verify district reach separately from regular movement. Observe real walking for clipping, floating and blocked passages.

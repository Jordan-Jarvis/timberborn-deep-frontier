# Review of 0.8.6 to the meltdown queue fix (2026-11-09)

Scope: every change from `7090abb` to `d418394` (releases 0.8.6, 0.9.0, 0.10.0 to 0.10.3, the radioactive-source overflow fix, the debug building visibility crash, Reactor Bot faction validation and `f91bdb7`, the queued-meltdown fix), plus the larger features they touch: Reactor Bot workplaces, Modular Warehouse, Deep Drill and mineral sources, the meltdown crater and blast, the Fisher Flag and construction stages. `src/FluidsApi` was excluded; Deep Frontier does not call into it.

Method: read the diff and the affected code paths, then checked each suspicion against Timberborn 1.1.2.8 code decompiled from the installed game (not committed). Three read-only sub-reviews covered faction assumptions, the mineral lifecycle, and the UI and Harmony patches; every finding below was re-checked before it was acted on. Static evidence only: the game was not launched. Line numbers refer to `main` after the fixes.

### 1-6. Non-Iron Teeth factions still crashed after 0.10.3

0.10.3 gated only `ReactorBotSettings.PostLoad` and `ReactorBotLeakSettings.PostLoad`. Native `NeedManager` takes its needs from `FactionNeedService.GetBeaverNeeds/GetBotNeeds`, and native `GoodService` keeps only the current faction's goods (`GameGoodFilter` over the faction's collection ids). Deep Frontier appends its needs and goods to the Iron Teeth collections only (`Data/NeedCollections/NeedCollection.IronTeeth`, `Data/GoodCollections/GoodCollection.IronTeeth`). Several components and services that run for every faction then threw:

1. `ReactorBot` is decorated on every `BotSpec`. `InitializeEntity` → `ApplyNeeds` → `Disable("ReactorCharge")` threw "bot has no need ReactorCharge" for every Folktails bot, both loaded and newly assembled (Folktails bots need Biofuel, Catalyst and PunchCard). Fixed at `SuperBots/ReactorBot.cs:92`: outside Iron Teeth the bot stays native and ordinary. `Queue` refuses, and the panel hides (`ReactorBotPanel.cs`).
2. `RadiationExposure` is decorated on every `BeaverSpec`. Its first `Tick` threw "Beaver need 'Irradiation' is missing", so a new non-Iron Teeth game crashed as soon as it was unpaused. Fixed at `Radiation/RadiationExposure.cs:103`: the component disables itself outside Iron Teeth. `RadioactiveZombie` stays inert there because native `GetNeed` returns the null need, which is never active.
3. `MineralDepositFragment.ShowFragment` (`DeepOre/DeepOrePanels.cs:125`) and `HumanRecordCachePanel.UpdateFragment` (`Narrative/NarrativeJournal.cs:220`) call native `GetGood` with Iron Teeth goods, which throws "GoodSpec with id … not found". Built-in map setup places these objects in every new game. Both panels now hide outside Iron Teeth.
4. `RadiationStorageService.Process` converted stored Water into the Iron Teeth `ContaminatedWater` good. Native stockpile visualizers then call `GetGood` on it. This is reachable because the radioactive tide is on by default. Fixed at `Radiation/RadiationStorage.cs:42`.
5. `BuiltinMapSetup` placed Iron Teeth mineral sources in non-Iron Teeth games:
   - Native `YielderInitializer` gives a yielder whose good is not loaded a yield of 0. `MineralDeposit.SetAmount` (reset, then decrease by capacity minus amount) produced negative stock, every placement was reported FAILED, and the "setup failed" dialog appeared.
   - Every such source then counted as empty and recovered 20 every 5 days to a negative amount, and that value was saved.

   Fixes:
   - The setup records the new outcome `OtherFaction` and places nothing (`MapSetup/BuiltinMapSetup.cs:128`).
   - The missing-sources notice is Iron Teeth only (`MapSetup/MineralMapNotice.cs:48`).
   - A deposit whose good is not loaded holds nothing and never recovers, and `SetAmount` on it throws (`MineralDeposit.cs:59`). This covers custom maps and existing saves.

   The map editor is unaffected: native `MapEditorGoodFilter` makes every good usable there.
6. The patched worker-type toggle offered and sold a Reactor Bot unlock on Folktails workplaces; enabling it emptied the workplace for bots that cannot exist. The option is now unclickable outside Iron Teeth, and the district default refuses it (`SuperBots/ReactorBotWorkplaceUnlocks.cs:128`, `ReactorBotWorkplace.cs:242`). With fix 1 in place, the dev Reactor Bot generator would have thrown "no bot took the Reactor Bot birth"; it now spawns nothing and logs a warning (`ReactorBotGenerator.cs:68`).

One rule decides all of this: `DeepFrontierFaction.Applies` (`Scripts/DeepFrontierFaction.cs`, native `FactionService.Current.Id == "IronTeeth"`). Iron Teeth validation is still strict.

Timing evidence: `FactionService.Load` sets `Current` from the save or the new-game configuration. Native `SingletonLifecycleService.LoadAll` loads every singleton first, then runs `WorldEntitiesLoader`. `SingletonListener` collects singletons in injection order, so an injected `FactionService` loads before its dependants.

Regression: the `reactor-faction` gate runs the compiled gates for Folktails, Whitepaws, Emberpelts and Iron Teeth: `ReactorBot.InitializeEntity`, `RadiationStorageService.Tick`, and `ReactorBotWorkplaceUi.ReactorState` and `SelectReactor`. It now makes 29 checks. Restoring the ungated `ReactorBot` or storage code fails it (negative controls run in the scratch mirror).

### 7. A hospital without medicine admitted and held medical-only patients

Since 0.10.0, ordinary care no longer needs medicine (the `HospitalSupplyAvailability` prefix), so `Attraction.IsUsable` stays true without it. Native `AttractionNeedBehavior` offers the hospital for every need in its static effect list: `DistrictNeedBehaviorService` groups behaviors by `AttractionSpec.Effects`, and `ActionPosition` checks only `IsUsable` and a free slot. Its `MaxValueNeedsAreActive` keeps a visitor until every SatisfyToMaxValue need is full.

Beavers needing only decontamination or radiation care were therefore drawn away from Decontamination Pods and kept, untreated, in the thirty beds. Irradiated beavers stayed until their untreated clock killed them, because `RadiationExposure` correctly does not count care without medicine. Before 0.10.0 the hospital was simply unusable without medicine.

Fixed by two postfixes (`HospitalMedicalVisits.cs:48` and `:58`). While `Hospital.CanProvideMedicalTreatment` is false:
- the hospital is not offered to a beaver without an Injury or ChippedTeeth need;
- no patient is kept for medical needs alone.

Mixed patients are still admitted and released once their ordinary care is complete. The members and the private method's non-inlinable IL size (well above Mono's 20-byte limit) are verified at mod start; the patches now install through `NativePatches` (`2dce084`). Not yet observed in game; see the checks below.

### 8. Migrated empty ore sources could start a second recovery clock

For a 0.8.x `DeepFrontier.DeepOreDeposit` saved empty, `SetAmount(0)` resumed the trigger before the saved progress was applied. Native `TimeTrigger.FastForwardProgress` resumes a trigger that was running. If the saved progress completed it, `Recharge` refilled the source to 20 and a fresh countdown started on the full source, so it refilled again 5 days later. The clock is now paused before fast-forwarding (`MineralDeposit.cs:74`). Current 0.9.0 saves were not affected: their trigger was not running at that point.

### 9. Half-migrated documentation

The following still described district-pool drilling, a `BuildingPlacer` for the source, `DeepOreDepositSpec` save keys, and stone outcrops that "run out":
- comments in `BuiltinMapSetup`, `map_setup_content.mjs`, `validate_deadlocks.mjs` and `validate_vertical_slice_content.mjs`;
- `docs/maps.md`, `docs/deadlock-audit.md` and `map_loop_requirements.json`.

They are corrected, and the saved-components table now lists the native `Yielder:Mineral` stock, the `DeepFrontier.MineralDeposit` clock and both migrated formats. Text only.

### 10. Building passage statics outlived their scene

`BuildingPassages.GroupId`, `Nodes`, `Linked` and `Passages` were statics reset only by the next game's `PostLoad`. While the next save loaded, the edge-blocking, obstacle and access patches read the previous game's group id, so native blocking of whichever group reused that id could be skipped. A later unblock of such an edge would then throw "Can't unblock edge". The native-safety audit fixed this concurrently in `432e696`: the passages are now a scene-owned instance that is cleared on unload.

### 11. Hospital supply readouts count medicine (not fixed)

Native `GoodConsumingBuildingFragment.UpdateProgressBar` shows `HoursUntilNoSupply()`, the minimum over every consumed good including medicine. It therefore reads 0.0 h while ordinary care runs without medicine. When water or extract runs short, `GoodConsumingBuildingStatusInitializer.CheckIfSupplyIsUnavailable` also checks district stock of medicine.

Not changed:
- `HoursUntilNoSupply` must keep including medicine, because it decides `CanProvideMedicalTreatment`.
- Correcting the bar needs a further patch of native UI.
- The hospital's own "Needs medicine" status already reports a medicine shortage when a medical patient is inside.

The owner can choose to add an `UpdateProgressBar` postfix for hospitals that excludes medicine.

### 12. Warehouse capacity is split over all five slots (owner decision)

Since 0.10.1 `ActiveSlots` is always 5 (`ModularStorage/ModularWarehouse.cs:97`), so a core alone with one selected good holds 120 of 600. In an existing save, a single-good core's excess (for example 480 of 600) becomes native unwanted stock and is hauled out on load. The 0.10.2 acceptance asserts 120 per slot deliberately. If unintended, divide by the number of selected slots, at least 1, and refresh every selected good when a selection changes.

### 13. Teleporter and zipline stations became linkable (needs in-game check)

Since 0.10.0 `BuildingPassages.Linkable` accepts any finished `Building` with `BuildingAccessible` except tube stations. Teleporter Station's `Teleporter` and `TeleporterRing` (both Iron Teeth, from a required dependency) and vanilla Folktails `ZiplineStation` qualify. They are path buildings with their own zipline edge group, the same kind of transport port that was excluded for tube stations after a native group conflict.

Not changed without evidence. The suggested check and fix: place a Teleporter beside a workplace and confirm a passage forms and teleporting still works. If it does not, exclude `PathSpec` or `ZiplineStationSpec` buildings in `Linkable`.

### 14-18. Smaller items (not fixed)

- **14.** The warehouse slot passes its whole row as the native picker's anchor (`ModularWarehousePanel.cs:127`). The native controller disables outside-click dismissal while the mouse is over the anchor, so clicking Unselect leaves the picker open with the old highlight. Using the Selection button as the anchor also moves the popup, which was visually approved with the row anchor, so it needs re-approval.
- **15.** `MineralMapNotice` marks itself shown only when it shows a dialog. If nothing was missing at first, a source type later lost (crater, dev delete) produces the notice mid-campaign. The message is still true; left as is.
- **16.** `validate_radioactive_recovery.mjs` reports net-positive recycling: Enriched Fuel uses 12 radioactive water and recovers up to 26.5; Fuel Reprocessing uses 6 and recovers up to 22. The user chose to allow recycling on 2026-11-06 and the validator deliberately has no lossy-loop gate. This is a balance call for the owner.
- **17.** The manifest description and `workshop/description.bbcode` still say "46 goods and 68 recipes", from 0.8.0; there are now 72 recipe blueprints. The repo does not define the counting rule, and the Workshop text is the owner's.
- **18.** The `PassageObstacles` postfix also changes what native `UnsetObstacle` sees. A linked doorstep on a district crossing's middle cell might then throw when the crossing changes. This was suggested by a sub-review and not confirmed.

## Checked and found sound

- **Queued meltdowns (`f91bdb7`).**
  - Native `TickableBucketService` ticks singletons in bucket 0 before the entity buckets. A reactor therefore requests in tick N and `MeltdownService` executes in tick N+1, outside entity iteration.
  - `EntityService.Delete` sets `EntityComponent.Deleted` before the `IDeletableEntity` callbacks and defers `Object.Destroy`. The batch is a copy, so dev `ForceMeltdown` or a player deletion during the batch is safe.
  - A reactor destroyed by an earlier blast in the same batch is skipped; separated reactors both execute; duplicate requests run once.
  - Characters killed by the first blast are skipped by the `Alive` check. Enterers of a destroyed reactor are ejected natively.
  - `GameSaver` calls `Ticker.FinishFullTick` before writing, so a save holds heat 1 and the meltdown is requested again on the first tick after load.
  - The blast-membership invariant stays strict for live reactors. The queue harness reproduces the old failure.
- **Waste leaks:** unchanged contracts; OK.
- **Teleporter Station recovery:** the scans run from `TeleporterNetwork.PostLoad`; the teleporter's own `== null` checks and try/catch handle the transpiler's null. Since `432e696` it is installed at mod start.
- **Negative unemployment:** the build-288 "unresolved trigger" is explained by the Teleporter dead-character restore (reproduced in build 292, fixed in build 293). The remaining custom staffing paths (`ReactorBotStaffing`, `SpecialistStaffing`) require living characters and use native `AssignWorker` and `UnassignWorker`.
- **Radiation source mixing:** native-order replay, withdrawal formula and kernel excess are covered by the compiled harness. Concurrent rows only read `_sourceCells`.
- **Reactor Bot faction validation (`1fd5a0d`):** the startup gate is correct; findings 1 to 6 extend it to the remaining paths.
- **Mineral sources (Iron Teeth):**
  - nothing native deletes a non-Ruin yielder at 0, and flags and pits find recovered sources (the closest-yielder search skips empty ones);
  - reservations never exceed stock, and the load order runs Load, then InitializeEntity, then `ResolveLoadedReservation`;
  - the native yielder always saves the stock;
  - the map editor never runs recovery;
  - the timer service removes a trigger before calling it;
  - subscription in `InitializeEntity` and unsubscription in `DeleteEntity` balance;
  - the Scavenger Flag retriever postfix matches the native signature.
- **Warehouse picker adapter:**
  - Escape, outside clicks, closing the panel and deleting the building all close the native picker before the throwaway cache is destroyed;
  - the cache registers nothing global;
  - `SetGood` is not re-entered;
  - shares add up to the network capacity;
  - old saves with closed slots load with empty Accept slots.
- **Hospital supply prefixes:** they match the native bodies except for medicine, and keep fractional doses. `CanProvideMedicalTreatment` turns false once the dose and stock are gone.
- **Building passages:** the exit-finished ordering claim in `Leave` matches native code, and unlinking iterates over copies.
- **Debug building visibility:** the native toggler alternates hide and show, so no model is hidden twice.
- **Workplace inventory rows:** the prefix matches native `AddRecipeRows`, and the native caller always passes a recipe.
